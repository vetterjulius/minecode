# Research Design (Draft)

Status: draft for discussion. Goal, venue and budget are not decided yet (see section 9). Nothing here is a result; all numbers are placeholders to be set by the pilot.

## 1. Research question

> Does generating an application from a declarative feature registry with architectural knowledge (Minecode) improve the correctness, security, cost and maintainability of agent-built SaaS applications compared with an agent writing the code freely?

The claim behind Minecode is "the AI describes, the engine decides". The claim is only worth something if it can be measured against an agent that simply writes the code. Today the repository contains no such measurement.

## 2. Related work and gap

- **Declarative app specs.** Wasp compiles a declarative description of a full-stack app. Its team moved from its own language to a TypeScript spec in 2026 and argues that a compile-time model of the whole app also makes AI-generated code more predictable ([Wasp blog](https://wasp.sh/blog/2026/05/13/new-language-for-web-dev-was-a-mistake)). This is a claim from practitioners, not a controlled study.
- **Agentic app-generation benchmarks.** "From Prompt to Product" benchmarks agentic app generators with a human-centered protocol ([arXiv:2512.18080](https://arxiv.org/abs/2512.18080)). Its emphasis is on how generated apps look and work at first use; long-term usability, maintainability and security are outside its scope.
- **Gap this project can fill.** Executable, multi-tenant correctness and security checks, cost per accepted app, run-to-run variance, and the cost of a follow-up change.

A systematic literature search (software product lines, feature-oriented generation, LLM code generation with constrained intermediate representations) is still to be done before any paper claims novelty.

## 3. Hypotheses

- **H1 Correctness and security.** With Minecode, fewer generated apps leak data across tenants and more pass hidden acceptance tests.
- **H2 Cost.** With Minecode, the agent needs fewer tokens and less wall-clock time per accepted app.
- **H3 Stability.** Repeated runs of the same task vary less in outcome (pass rate, files produced) with Minecode.
- **H4 Maintainability.** A follow-up requirement is implemented with a smaller diff and fewer regressions when the app was generated by Minecode.
- **H5 Limits (negative hypothesis).** For tasks outside the feature catalog, Minecode degrades the result relative to free generation unless extension points are sufficient. This bounds the claim and must be reported even if it is unfavourable.

## 4. Conditions

| Id  | Condition                                                                                  | Purpose                                |
| --- | ------------------------------------------------------------------------------------------ | -------------------------------------- |
| A   | Agent writes the app freely from the requirements                                          | Baseline                               |
| B   | Agent uses Minecode via MCP: composes a blueprint, engine generates, agent adds extensions | Treatment                              |
| C   | Agent starts from a fixed, well-known SaaS starter template and edits it                   | Controls for "any good scaffold helps" |

All conditions use the same model versions, tool budget, timeout and acceptance checks. Model identifiers and dates are recorded per run.

## 5. Tasks

30 to 50 requirement sets for B2B SaaS applications in three tiers:

1. **In catalog:** every needed capability exists as a feature (for example tickets plus organizations plus billing).
2. **Near catalog:** needs one small custom entity or page next to existing features (tests extension points).
3. **Out of catalog:** needs behaviour the registry does not know (tests H5).

Each task ships a natural-language requirement, a machine-checkable acceptance suite hidden from the agent, and one follow-up requirement for H4. Tasks are written and frozen before any treatment run; a second person reviews them for bias towards Minecode's feature names.

## 6. Measurements

Automatic oracles, most of which already exist in this repository in some form:

| Measure                | Oracle                                                                                                                                          |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Builds and type-checks | `tsc --noEmit`, `next build` (as in `pnpm verify:examples`)                                                                                     |
| Schema applies         | Run migrations on PostgreSQL (PGlite harness)                                                                                                   |
| Tenant isolation       | Seed two organizations, run reads and writes as the other tenant, count successful leaks (the existing RLS integration tests are the prototype) |
| Internal consistency   | Every table, column and fetch target used by the app exists (the existing consistency test is the prototype)                                    |
| Functional correctness | Hidden acceptance suite (API level first, browser level later)                                                                                  |
| Security smells        | Static analysis (for example Semgrep rules for missing auth, secret exposure) and a secrets scan                                                |
| Cost                   | Input and output tokens, tool calls, wall-clock time, converted to money with the price list recorded at run time                               |
| Stability              | Variance across repeated runs                                                                                                                   |
| Maintainability        | Diff size, files touched and regression failures for the follow-up requirement                                                                  |

Human judgement is limited to a sample audit of oracle verdicts, to detect harness bugs. During development of this repository, a purely static check found 30 table, column and endpoint mismatches in generated apps that built and type-checked cleanly; the oracle set therefore has to be validated, not trusted.

## 7. Procedure and statistics

- Pilot first: 10 tasks, 3 conditions, 3 runs each, to find harness bugs and estimate variance.
- Main study: at least 5 runs per task and condition, sized from the pilot's variance.
- Paired comparison per task (same task under each condition). Report effect sizes with bootstrap confidence intervals; use Wilcoxon signed-rank or a mixed-effects model for pass rates, with task as a random effect.
- Preregister hypotheses, tasks, oracles and analysis before the main study.
- Publish tasks, oracles, run logs and the generated apps so results can be reproduced.

## 8. Threats to validity

- **Catalog bias.** Tasks may favour what Minecode already contains. Mitigated by tiers 2 and 3 and by independent task review.
- **Harness bias.** Oracles may match Minecode's conventions (snake_case, RLS layout). Oracles must test behaviour, not structure.
- **Contamination and model drift.** Models may have seen similar apps; versions change. Pin versions, log dates, repeat on a second model if budget allows.
- **Stack specificity.** One stack (Next.js plus Supabase) limits external validity. A second, minimal stack adapter would show how far the findings generalize.
- **Developer is evaluator.** The author of the system designs the study. Preregistration, published artifacts and an external reviewer reduce this.
- **Condition C fairness.** The starter template must be chosen before seeing results.

## 9. Open decisions

1. What is the goal (paper, thesis, internal evidence) and the target venue? This sets the required rigour and timeline.
2. Budget for model runs. Estimate as tasks x conditions x runs x (average tokens per run x price per token); the pilot yields the average.
3. Which model families to include.
4. Whether to add a second stack for generalization.

## 10. Dependencies on engineering work

The study needs these parts of Minecode, in this order:

1. Generated apps that build and enforce tenancy in the database (done for the reference apps).
2. Route-level permission checks and seeded roles (open), otherwise security results mix engine gaps with agent mistakes.
3. A file ownership manifest so a follow-up requirement can be applied without overwriting custom code (open); needed for H4.
4. A machine-readable run interface for the agent (MCP tools exist; knowledge and validation tools are partly missing).
5. The evaluation harness itself (new): runs a condition, collects tokens and artifacts, applies the oracles, stores results.
